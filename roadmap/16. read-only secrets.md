# Step 16: Read-only secrets

Goal: the server reads its secret files and never writes them (`../docs/decisions.md`, Configuration: secrets are read, never written). A missing or empty secret file is a startup error naming its variable; for the keys, the error says how to make one. Asked by the CE's compose (`ce/roadmap/00. global.md`, step 2), which mounts every secret as a read-only file, the Docker way.

A breaking `0.x` release (`feat(core)!`, `0.17.0`): a deployment relying on generated keys stops at startup until it writes its keys.

## Order across repositories

`web` and `cli` run their CI against `core:0-rc` and write **empty** key files there: the first `rc` with this change would break both. So, first:

1. **`web` and `cli`**: their CI generates the keys (the `server-files` step), as their `scripts/dev.sh` already do. Works with every `core`, old and new. Committed to their `dev` before anything below reaches `core`'s `dev`.
2. **This step**, on `core`'s `dev`, then released.

## The server

- **`config::read_secret` refuses an empty file** (only whitespace counts as empty): `Error::EmptySecret { name, path }`, "the secret file {path} (from {name}) is empty". It's every `X__FILE` variable's reader: `DATABASE_URL__FILE` gets a clear error instead of sqlx's on an empty URL.
- **`SecretKey::load`** replaces `load_or_generate`: reads through `read_secret` (one reader, one missing-file and one empty-file error), then parses 64 hex characters. `InvalidKey`'s message gains the fix: "expected 64 hex characters (make one with `openssl rand -hex 32`)", and so does `EmptySecret` when the variable is a key's: the error a first-time self-hoster meets is the one that tells them what to run.
- Gone: the generation, `Error::KeyNotWritable`, its test (`empty_and_read_only_is_an_error`) and `generates_into_empty_file_then_reloads_it`; `getrandom` stays if anything else uses it, else it goes too.
- Tests: an empty key file is `EmptySecret` naming the variable, with the `openssl` hint; an empty `DATABASE_URL__FILE` is `EmptySecret`; the valid and invalid key tests stay.

## Around it

- **`tests/smoke.rs`** writes generated keys (64 hex characters) instead of empty files.
- **`scripts/dev.sh`** generates `data/secrets/server_key` and `data_key` once (`openssl rand -hex 32`, kept when non-empty), instead of empty files. An existing dev setup already holds the generated keys: nothing to redo.
- **`CONFIGURATION.md`**: `SERVER_KEY__FILE` and `DATA_KEY__FILE` say "64 hex characters, e.g. `openssl rand -hex 32`", the generation sentences go; the intro states the rule (secret files are only read; missing or empty stops the server).
- **`try/`** already generates its keys: unchanged.
- **`../docs/BREAKING.md`**, `core 0.17.0`: the keys must exist (`openssl rand -hex 32 > server.key`), an empty file stops the server; an instance that ran with generated keys already has them in its files and is unaffected.

## Done when

- CI green; `0.17.0` released.
- `web`'s and `cli`'s CI green against `core:0-rc` carrying the change, before it's released.
