# Step 12: The client library

Goal: `theca-client`, the engine every client is built on (the CLI first, the web app through WASM): the API, uploads and downloads written once, natively and in the browser. Proven end to end against the real server binary.

Design: `../docs/decisions.md` (Architecture: one client engine; Upload flow; Downloads; API contract; Compression), `roadmap/00. global.md` (Testing).

## The API

- **Hand-written over the `common` types**: no `progenitor`. The client lives in the server's workspace and is released with it; the CLI (its own repository) uses the released `theca-client` crate, never the API directly: the API defined by one crate, used by another binary through a pinned release. One generic `call` (method, path, JSON body, typed answer; errors as `ApiError` with their `code`), and a short typed method per endpoint the engines and the CLI need (`login`, `me`, `libraries`, `children`, `lookup`, `upload_urls`, `announce`, `cancel`, `commit`, `download`, folders, moves, trash, versions, search, app passwords).
- **Auth**: a `Bearer` token (CLI: an app password or a session token) natively; the browser's cookie in WASM (`credentials: include`, the session cookie never reaches JavaScript).
- Checks `/api/version` once: a server without `v1` is a clear error.

## Uploads

`upload(source, target, options, progress, cancel)`, the protocol of decisions.md, once for every client:

1. **Hash pass**: read the source chunk by chunk (FastCDC, `xxh3_128`), keep only hashes and sizes (any file size, little memory).
2. **Lookup**, batched: which chunks to upload.
3. **Upload pass**: re-read only those chunks (by offset), compress per the policy, declare in batches under `max_pending_uploads`, `PUT` to the presigned URLs with their signed headers, a few in parallel (4 by default: 32 MiB at most in memory), announce. A `412` means already uploaded.
4. **Commit** (new file, or a new version on a base): `chunk_missing` re-uploads those chunks and commits again; `name_taken` goes back to the caller.
- **Keepalive**: during long uploads, the uploaded chunks are looked up again every 6 hours.
- **Cancel**: the pending chunks are cancelled (tombstoned) on the server.
- **Resume**: start again; ready chunks are skipped by the lookup. Nothing to store.
- **Retries**: network errors and `5xx` with backoff; an expired URL is requested again.
- Progress: bytes hashed, bytes uploaded, chunks skipped (deduplicated).

## Downloads

- `download(file, version, sink, options, progress)`: the manifest, chunks fetched in parallel from their presigned URLs, decompressed, written in order. **Checked against their hash by default** (a lying server or storage is caught); `verify: false` turns it off (`xxh3_128` runs at tens of GB/s: the cost is small next to downloading and decompressing). Native only in V1: the web app downloads through the server's streaming endpoint (`/files/{id}/content`, step 11), and through presigned URLs with a Service Worker in V2.

## Platforms

- A small `Platform` trait: the source's size and a range read, sleep, spawn, now. Native: tokio and `std::fs`. WASM: `Blob.slice`, timers, `spawn_local`.
- `reqwest` for HTTP on both (its WASM backend is `fetch`).
- **WASM package**: `wasm-bindgen` exports a thin API for the web app (`upload(file, parent, name, onProgress)`, `cancel`), built with `wasm-pack`. Published with the releases (step 14).

## Tests

- **The engines against a fake platform** (controlled clock, in-memory files): batching under the cap, parallelism bound, keepalive timing, retries, cancel, resume, `chunk_missing` and `412` handling.
- **End-to-end smoke test** (global roadmap): `crates/core/tests/smoke.rs` starts the real `theca-server` binary (env config, migrations at startup, a real port, open setup), then through `theca-client`: setup, login, upload (multi-chunk, on the filesystem and S3), download, compare, an edit uploading only new chunks, resume after an interrupted upload.
- WASM: built in CI (the existing `wasm` step); its platform code is exercised in the browser by the web app's end-to-end tests.

## Not in this step

- Local configuration and credentials: with the CLI, its only user in V1 (moved here when a second native client needs them). Proposed there: no OS keyring (it prompts after every update of an unsigned binary); an app password in a `0600` file, or `THECA_TOKEN`.
- The npm publication (step 14), E2EE (later).
