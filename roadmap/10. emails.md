# Step 10: Emails

Goal: the server sends emails (verification, password reset, invitations), and accounts come into existence three ways: self-registration (when allowed), an invitation that creates the account, and an owner adding an existing account to their organization.

Design: `../docs/decisions.md` (Email templates, Background jobs, Authentication), `../docs/features.md` (Identity).

## SMTP and the queue

- **Settings**: `smtp_host`, `smtp_port` (587), `smtp_tls` (`starttls`, `tls`, `none`), `smtp_username`, `smtp_password_file` (a path, like every secret), `smtp_from`. No `smtp_host`: emails stay queued, and features that need one say so (see Registration).
- **The `email` table is the queue** (recipient, template, params, attempts, next attempt, sent at, last error). Enqueueing is a row in the transaction that needs the email, so nothing is lost or sent twice for a rolled-back action.
- **Job `email_send`** (every 30 s; the runner from step 09): due emails, oldest first. **The token is created at send time**, in one transaction with the send (decisions.md): a failed send rolls the token back, the retry creates a new one. The queue never holds a token.
    - Retries with increasing delays (1 min, 5 min, 30 min, 2 h, 12 h), then given up (`last_error` kept, logged).
    - **The job reads the SMTP settings from the database at each run**, so they apply without a restart (the general settings reload stays step 13).
- `cleanup` also deletes sent and given-up emails after 30 days (they hold addresses).
- `lettre` (rustls with `ring`, like everything else).

## Templates

- `askama`, one context struct per email, HTML and text, English (`verification.en.html`, `.txt`), a shared layout. Instance name and public URL as the only branding.
- Links point to the web app (`{PUBLIC_URL}/verify?token=...`, `/reset?token=...`, `/invite?token=...`), which calls the API.

## Tokens

- One-off tokens (`email_verification`, `password_reset`, `invitation`): single use (`revoked_at`, reason `used`), and creating one revokes the previous unused ones with the same usage and resource (db.md). Lifetimes: verification 7 days, reset 1 hour, invitation 14 days.

## Registration

- Setting **`registration`** (`closed` by default, `open`). Open needs SMTP: without it, `POST /auth/register` answers `503 email_unavailable`.
- `POST /auth/register` `{ email, password }` → an **unverified** account, its password, its **personal organization**, and a verification email. Always `202`, whether the email was free or not (no account enumeration); a taken email gets a "someone tried to register with your address" email instead.
- **Self-registered unverified accounts can't log in** (`403 email_not_verified`, and `POST /auth/verify/resend`). Otherwise someone could register a victim's address first (pre-account takeover). They're deleted after 7 days (`cleanup`), which frees the address.
- `POST /auth/verify` `{ token }` → verified, and logged in.
- **`oidc_link_by_email` only links verified accounts** (same pre-takeover, through a provider).
- **OIDC sign-up**: an unknown identity from an **instance-wide** provider creates an account when registration is open (verified if the provider says the email is; no password; personal organization). From an organization's provider: still refused (creating members on the fly is later).

## Password reset

- `POST /auth/password/forgot` `{ email }` → always `202`; a reset email if the account exists.
- `POST /auth/password/reset` `{ token, password }` → sets the password (adds one to an OIDC-only account: the inbox proves ownership), **verifies the email, revokes every session**. TOTP stays required.

## Invitations

- **Personal organizations**: `organization.personal_of` (the account; unique; NULL for company organizations). Created at self-registration and OIDC sign-up only. **Never another member** (trigger), and the owner is that account (composite FK). Its name doesn't matter (the web app shows "My files"); memberships expose `personal`.
- `POST /organizations/{id}/members` `{ email }` (the owner, from a full session; never into a personal organization), one endpoint, the server picks:
    - **an account exists**: its user row is created, **joined at once** (direct join; the person gets a notification email when SMTP is set);
    - **no account**: an **invitation** email. The phantom user (`joined_at` NULL) is created now on a new account **without identity**, so the member list shows it pending.
- `POST /invitations/accept` `{ token, password }`: the invited account sets its password, is verified (the link proves the inbox), joins, and is logged in. Works with registration closed.
- `GET /organizations/{id}/members`, `DELETE /organizations/{id}/members/{user}` (the owner; the owner can't be removed). Removing a pending member cancels the invitation.
- `cleanup`: expired invitations delete their phantom user, and its account if it has no identity and no other user (decisions.md).

## Schema changes

- `organization.personal_of` (+ composite FK on the owner, trigger refusing other members).
- Token usages: `password_setup` goes (the invitation covers it).
- `email`: knows when it was given up.

## Not in this step

- Rate limiting of these endpoints (step 13), custom templates (EE), other languages.

## Tests

- **Mailpit** receives the emails (dev compose, and its binary in the CI image like Garage); tests read them through its HTTP API, filtered by recipient (unique per test). Its chaos mode makes SMTP fail, for the retries.
- Queue: sent once; a failed send retried later with no token left behind; given up after the last attempt; the link's token works once, and an older one stops working when a new one is sent.
- Registration: closed refused; open creates account, organization, email; taken email: same answer, different email; unverified can't log in; verification logs in; unverified accounts expire.
- Password reset: same answer for unknown emails; reset sets the password, revokes sessions, keeps TOTP; an expired or used token refused.
- OIDC: sign-up through an instance-wide provider when open; link by email skips unverified accounts.
- Members: adding an existing account joins it at once; a new address gets an invitation, accepted with a password (logged in, verified); a used or expired invitation refused; expired invitations cleaned up; removing members; nothing added to a personal organization; only the owner manages.
