# Step 03: Server foundation

Goal: a server that starts from environment variables, checks and migrates its database, loads its settings, and answers its first two endpoints. Everything later steps plug into.

Design: `../docs/decisions.md` (Configuration, Schema and migrations, API contract).

## Startup configuration (environment only)

| Variable | Default | Notes |
|---|---|---|
| `DATABASE_URL__FILE` | required | Secret (the URL contains the password) |
| `LISTEN_ADDR` | `0.0.0.0:8080` | |
| `PUBLIC_URL` | required | Used in emails and links later |
| `JWT_KEY__FILE` | required | Secret. Empty file → the server generates a key into it |
| `RUST_LOG` | `info` | Standard `tracing` filter |

- **`__FILE` only for secrets**: a secret exists only as `X__FILE` (path to a file holding the value, trailing newline trimmed), everything else only as a plain variable. Secrets for now: `DATABASE_URL__FILE`, `JWT_KEY__FILE`.
- **Dev**: `scripts/dev.sh` also writes the secret files in `data/secrets/` (the database URL, an empty JWT key file) and points `.env` at them. `.env` keeps a plain `DATABASE_URL` too, read only by sqlx's macros at compile time, never by the server.
- No prefix on variable names: the server runs alone in its container.
- **`.env` loaded in debug builds only** (`dotenvy`), so `cargo run` works after `scripts/dev.sh`; release builds read the real environment only.

## JWT key

- Read from `JWT_KEY__FILE`. Empty → generate 32 random bytes, write them (hex), use them. Empty and not writable → startup error with a clear message.
- Only loaded and held here; signing comes in step 06.

## Database

- `sqlx` pool on the URL read from `DATABASE_URL__FILE`.
- **Startup check**: Postgres ≥ 17 and the database created with the built-in `C.UTF-8` collation; otherwise refuse to start with a clear message (case-insensitive name uniqueness depends on it).
- **Migrations embedded** (`sqlx::migrate!()`) and run at startup; a failed migration stops the server.
- **First migration**: the `setting` table only. Each later step adds its own migration for its tables.

## Settings

- `Settings` struct: one typed field per setting, each with its key, default and parser. Starts with `instance_name` (default `Theca`) and `gc_grace_period` (default 24 h), to exercise the mechanism.
- Loaded at startup: missing key → default, unparsable value → startup error, unknown key → warning.
- Held in memory, shared with handlers. Writing settings comes with the admin API.

## HTTP

- `axum` server on `LISTEN_ADDR`, graceful shutdown on SIGTERM / Ctrl-C.
- **`GET /api/health`**: the probe for Docker, orchestrators and monitoring.
    - **Contract (never changes): the HTTP status.** `200` = ready to serve, `503` = not ready. The body is informational and may grow: `{"status": "ok", "checks": {"database": "ok"}}`. Later checks plug in (step 09: jobs failing repeatedly).
    - Each check has a short timeout (2 s), so a hung database makes the probe fail instead of hang.
    - Public, but reveals nothing beyond ok / failing per check (no versions, no error details; those go to the logs).
- **`theca-server healthcheck`**: a subcommand that calls `/api/health` on `LISTEN_ADDR` and exits `0` or `1`. Production images won't ship `curl`, so Docker's `HEALTHCHECK` (in the `ce` repo) runs the binary itself. Plain `std::env::args`, no CLI framework.
    - The server only listens once migrations and settings are loaded, so the probe fails during startup; the `ce` Dockerfile gives it a start period.
- **`GET /api/version`**: server version and supported API majors (`["v1"]`).
- **OpenAPI**: handlers and types annotated with `utoipa`. `openapi.json` committed at the repo root; a test generates the spec and fails if the committed file differs (`UPDATE_OPENAPI=1 cargo test` rewrites it).

## Errors

- `theca_core::Error` (thiserror) grows variants for configuration, database, migration, settings and I/O errors; each startup failure prints what to fix.

## CI

- Postgres 17 service in the Woodpecker pipeline (same `initdb` arguments as `docker-compose.yml`).
- `sqlx-cli` added to the CI image; `scripts/ci.sh` runs migrations then `cargo sqlx prepare --check`, and `.sqlx/` is committed.
- Compile with `SQLX_OFFLINE=true` in CI, so builds never depend on the live DB.

## Tests

- Secrets from files: value read and trimmed, missing variable, missing file.
- JWT key: existing, generated into an empty file, unwritable file.
- Settings: defaults, stored values, invalid value, unknown key (`#[sqlx::test]`, one fresh DB per test).
- Collation check rejects a database created with another collation.
- `/api/health` (`200`, and `503` with the DB down) and `/api/version` through the router, without a network socket.
- `theca-server healthcheck` exits `0` against a running server, `1` otherwise.
- OpenAPI file up to date.

## Done when

- `scripts/dev.sh && cargo run -p theca-core` starts the server, migrates, and `curl localhost:8080/api/health` returns `200`; `theca-server healthcheck` exits `0`.
- `scripts/ci.sh` and the Woodpecker pipeline pass, with Postgres.
