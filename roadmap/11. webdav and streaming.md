# Step 11: WebDAV and streaming

Goal: libraries mount as network drives (Finder, Windows Explorer, Nautilus, rclone, Cyberduck...), and the browser previews files natively, both served by one streaming reader over chunks.

Design: `../docs/decisions.md` (Presigned URLs: "WebDAV: the server streams", Architecture, E2EE), `../docs/features.md` (WebDAV, previews).

## The streaming reader

- **One reader over a version's chunks**, seekable: an offset maps to a chunk through the cumulative plain sizes; the chunk is fetched from its backend, decompressed, and the right slice served. The last chunk read stays cached (sequential reads hit it), so a stream costs one backend `GET` per chunk.
- Used by WebDAV `GET` (with `Range`) and by the preview endpoint. The server streams: a redirect can't split one response across chunks nor translate the client's `Range` offsets (decisions.md).

## Previews

- `GET /api/v1/files/{id}/content` (session cookie, so `<video src>` and `<img src>` work), `?version=` optional, `Range` supported, `Content-Type` from the name's extension, `ETag` = the version.
- **User content on the app's origin is an XSS risk** (an HTML or SVG file running script with the user's session). So every response gets `Content-Security-Policy: sandbox` and `X-Content-Type-Options: nosniff`, and types that can carry script (HTML, SVG, XML, JavaScript) are served as `text/plain` or as attachments, never rendered. (A separate content domain is the stronger fix, later if needed.)

## WebDAV

- **`dav-server`** behind `/dav/`, implementing its filesystem trait over nodes. **Every operation goes through the same core functions as the API** (decisions.md: one function per action, shared by the API and WebDAV): creating folders, renames and moves, copies, the trash, commits. Moving the access checks and validation out of the handlers into those functions is part of this step.
- **Authentication: app passwords only**, as HTTP Basic (the username is ignored; the password is the app password). Never the account password (WebDAV clients can't do TOTP or OIDC) nor session cookies (no CSRF to worry about). A read-only app password gets a read-only drive (`403` on writes).
- **The tree follows the app password's scope**:
    - the account: `/dav/` lists organizations (the personal one as `My files`), then their libraries;
    - an organization: `/dav/` lists its libraries;
    - a library: `/dav/` is its root.
    Two organizations with the same name get a ` (2)` suffix (organization names aren't unique).
- **Reads**: `PROPFIND` (size, modification time = the current version's date, `ETag` = the version), `GET` with `Range` through the streaming reader.
- **Writes**: a `PUT` is spooled to a temporary file (no memory limit to hit), then **chunked, hashed and deduplicated on the server** (the same `common` code as the clients), new chunks stored directly in the backend (no presigned URL: the server holds the bytes), and committed as a new version based on the current one (last write wins, like any WebDAV server). The quota is checked before storing.
- `MKCOL`, `DELETE` (to the trash), `MOVE` (rename, move, across libraries of the same organization), `COPY` (reuses chunks).
- **Locks**: in memory (`dav-server`'s lock store; one process). macOS Finder mounts read-only without `LOCK`, and Windows needs it to save.
- **Properties**: the live ones (size, dates, ETag, type). Dead properties (`PROPPATCH` of arbitrary XML) are accepted and not stored. Clients set them (Windows timestamps) without reading them back.
- E2EE libraries (later) are refused: the server can't read them.

## Testing

- **litmus** (the RFC 4918 conformance suite) runs in CI against a server started by the test, on a real port, with an app password. All groups run (`basic`, `copymove`, `props`, `locks`, `http`); the test parses litmus's per-test results and compares them to an **expected failures list** (the dead-property tests): any other failure fails the test, and so does an expected failure that passes (the list can't go stale). litmus goes into the CI image (Debian package); locally, the test runs it in Docker.
- Our own tests: the tree per scope; read-only refused; a `PUT` deduplicates against existing chunks and counts against the quota; `GET` with ranges across chunk boundaries and compressed chunks; preview headers (CSP, nosniff, HTML served as text); names refused by our rules (`409`/`400`), never renamed.

## Not in this step

- Storing dead properties: per-node properties, later (features.md). Per-node permissions: with the RBAC engine.
- A separate origin for user content, thumbnails, Service Worker previews (V2), CalDAV/CardDAV (never).
