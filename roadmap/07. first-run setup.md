# Step 07: First-run setup

Goal: a fresh instance is set up through one API call, protected by a token printed in the logs. The web wizard (in `web`) is a form in front of it.

Design: `../docs/decisions.md` (First-run setup, Storage backends, Configuration).

## Fresh or set up

- **Fresh = no instance admin** (`NOT EXISTS (SELECT 1 FROM account WHERE instance_admin)`). Read at startup, kept in memory (one process per database), flipped by the setup call: no restart.
- **A fresh server only serves the setup**: every other `/api/v1` route answers `503 setup_required` (one middleware check on the in-memory flag). `/api/health` and `/api/version` still answer.

## The token

- At startup, if fresh: a random token (128 bits), **in memory only** (a restart prints a new one; nothing to store or clean up), and a log line with the full URL: `{PUBLIC_URL}/setup?token=...`.
- `SETUP_OPEN=true` (env) turns the token off: the first visitor sets up (decisions.md: the risk is the admin's).
- Compared in constant time. A wrong token is an anomaly (`setup_token_invalid`); rate limiting stays in step 13.

## The API

- `GET /api/v1/setup` (public): `{ required, token_required }`, so the web app knows whether to show the wizard.
- `POST /api/v1/setup` (token in `X-Theca-Setup-Token`), once:
    - **admin**: email and password: an account with `instance_admin`, a password identity;
    - **organization**: its name; the admin is its owner (a joined user);
    - **storages**: one or more, each a name and a kind, filesystem (`path`) or S3 (`host`, `region`, `bucket`, `access_key_file`, `secret_key_file`, `path_style`), credentials as **file paths** only. All shared by the instance; **the first one is the instance default**. Names are unique (ignoring case);
- **Every storage is probed before anything is written**: write, read back and delete a small object. A typo in a path, bucket or key file fails the setup with the backend's error, instead of the first upload.
- **One transaction**, under an advisory lock that re-checks freshness: two concurrent setups can't both succeed (the second gets `409 already_set_up`).
- Answers like a login: the session cookie, and `Me`. The wizard continues as the admin.

## Schema

- `storage`: unique name per organization, ignoring case (`NULLS NOT DISTINCT`: shared storages share one namespace).

## Not in this step

- Settings (instance name, ...: settings are loaded at startup, nothing reloads them yet), instance-wide OIDC providers, SMTP, registration: admin API (step 13) and emails (step 10). The admin's TOTP: from their account, like anyone.

## Tests

- Fresh: only the setup answers (`503 setup_required` elsewhere); `GET /setup` says so.
- Wrong or missing token refused (anomaly); `SETUP_OPEN` accepts no token.
- Setup creates the admin, the organization (owned), the storages (the first as default); the admin is logged in and can create a library and upload into it.
- A storage that doesn't work (missing directory, wrong bucket, missing key file) fails the setup, and nothing is created.
- A second setup, and two concurrent ones: exactly one succeeds.
- After setup, the token is useless and every route answers normally, without a restart.
