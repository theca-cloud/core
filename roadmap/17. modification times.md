# Step 17: Modification times

Goal: each version keeps the modification time its client gives (the file's own, on the user's disk), and every view of a file shows it, instead of the upload time. Asked by V1's two-way sync (`rclone bisync` over WebDAV, `ce/roadmap/04. documentation.md`): with the upload time as its modification time and no way to set it, rclone with `vendor = other` ignores the server's times and **silently misses an edit that keeps the size**; with `vendor = owncloud` it trusts them, but finds every file's time differing from the client's and **uploads everything again at each run** (measured: 3 files of 3, then none with this step). Also what users expect: a folder copied through Finder keeps its dates.

A `0.x` minor (`feat(core)`), additive for the API: new optional fields.

## The data

- **`version.modified_at timestamptz NOT NULL`**: the client's time when it gives one, else the upload's (`created_at`). The migration is rewritten in place (before 1.0).
- **A touch updates the current version's time in place**: a commit with the current version's chunks creates nothing (decisions.md, Upload flow), and now sets that version's `modified_at` when its `modified` differs. A new version instead would copy the chunk list (thousands of rows for a large file) for the same content. No separate touch endpoint: that commit is the touch (over WebDAV, a `PUT` of the same bytes with a new `X-OC-Mtime`, what rclone sends). Only ever the current version: older ones keep theirs.
- Copying a file keeps it (a copy is the same content). Making an older version current only moves `node.current_version` (decisions.md, File history): the file then shows that version's own `modified_at`, nothing to write.
- Any instant Postgres stores is accepted (clients' clocks are theirs); outside that range, `400 invalid_modified`.

## Where it comes from

- **The API**: `Commit.modified` (optional, RFC 3339): the upload protocol's commit carries it.
- **WebDAV**: `X-OC-Mtime` on `PUT` (Unix seconds, ownCloud's and Nextcloud's header: what rclone's `vendor = owncloud`, and other clients, send), answered with `X-OC-MTime: accepted`. Without it, the upload time.
- **The client engine** (`theca-client`): `Source::modified()` (`Option<DateTime<Utc>>`, default `None`): a native file's metadata, a browser `File`'s `lastModified`, nothing for bytes in memory; the engine puts it in the commit. The CLI and the web app get it by bumping `core`, with nothing to write.

## Where it shows

- `Node.modified` and `NodeInfo.modified` (a new field): the current version's `modified_at`.
- `Version.modified` (new), beside `created_at` (when it was uploaded, and by whom: the history's own time).
- WebDAV's `getlastmodified`: the current version's `modified_at` (rclone then trusts it, at one-second precision).

## Tests

- WebDAV: a `PUT` with `X-OC-Mtime` reads back as `getlastmodified`, and answers `accepted`; without it, the upload time.
- API: a commit with `modified` shows in the node, its info and its version; an absurd one is `invalid_modified`; a copy keeps it; the same chunks with another time update the current version (no new version), an older version made current shows its own time.
- The engine: a `Source` with a time commits it (the smoke test, as the other engine tests).
- `rclone bisync` itself is tested in `ce` (its smoke test, rclone's image): same-size edits on both sides, with `vendor = owncloud`.

## Done when

CI green; released; `web` and `cli` bumped (their uploads keep their files' times); `ce` pins the `web` carrying it, and its bisync test passes.
