# Step 01: Skeleton

Goal: an empty but complete workspace, with every tool and check in place, so later steps only add code.

No logic, no DB connection (step 03).

## Workspace

```
Cargo.toml               workspace: members, shared dependencies, lints
rust-toolchain.toml      pinned stable toolchain + wasm32-unknown-unknown target
crates/common/           lib (native + WASM)
crates/core/             lib + thin bin
crates/client/           lib (native + WASM)
```

- **Edition 2024**, resolver 3.
- **`[workspace.dependencies]`**: every external crate declared once with its version; crates use `dep.workspace = true`.
- **Package names are prefixed**: `theca-common`, `theca-core`, `theca-client` (libs `theca_common`, `theca_core`, `theca_client`); directories stay `crates/common`, `crates/core`, `crates/client`. A lib named `core` would clash with Rust's built-in `core` crate, which derive macros (serde, thiserror) reference as `::core`. Prefixed names also avoid clashes on the Gitea registry.
- **`[workspace.lints]`**: `unsafe_code = "forbid"`; clippy `all` as warnings (CI turns warnings into errors).
- **`rust-toolchain.toml`** pins the toolchain version, so local builds and CI use the same compiler.

## Crates

- **`common`**: empty `lib.rs`. Must build for `wasm32-unknown-unknown` from day one.
- **`core`**:
    - `lib.rs` exposes `pub async fn run() -> Result<(), Error>` (for now: logs "starting" and returns).
    - `main.rs` only builds the tokio runtime and calls `theca_core::run()`, so a future EE binary can embed the server.
    - `Error` defined with `thiserror`.
    - Binary name: **`theca-server`** (the CLI owns `theca`).
- **`client`**: empty `lib.rs`. Must build for `wasm32-unknown-unknown` from day one.

## Local development

- **`docker-compose.yml`**: Postgres 17, port 5432, data in `./data/postgres` (bind mount, no named volume; `data/` is git-ignored). Starting over = `rm -rf data/`. Later dev services (MinIO/Garage, SMTP catcher) get their own `data/<service>` folder.
- **`scripts/dev.sh`**, idempotent, the one command to get a dev environment:
    1. `docker compose up -d --wait` (Postgres has a healthcheck, so the script returns once the DB is ready).
    2. Postgres user and database: created by the official image from its env on first start only.
    3. Writes **`.env`** (git-ignored) with `DATABASE_URL`, which `sqlx` macros read at compile time. Passwords are generated once: if `.env` exists, its values are reused.
    - Starting over: `rm -rf data/ .env`.
    - Later steps extend it with what they need (S3 buckets in step 05, SMTP catcher in step 10, ...).
- `sqlx-cli` documented as a dev prerequisite (used from step 03).

## CI (Woodpecker)

`.woodpecker/ci.yaml`, on every push:

1. `cargo fmt --all --check`
2. `cargo clippy --workspace --all-targets -- -D warnings`
3. `cargo test --workspace`
4. `cargo build -p theca-common -p theca-client --target wasm32-unknown-unknown`
5. `cargo deny check` (licenses compatible with AGPL and with a proprietary EE build, advisories)

A Postgres service is added to the pipeline in step 03, when the first test needs it.

## Repo files

- **`LICENSE`**: the official AGPL-3.0 text.
- **`deny.toml`**: allowed licenses, advisory database.
- **`CONTRIBUTING.md`**: two lines pointing to the shared one in `docs`.
- **`README.md`**: add build, run and test commands.
- **`CLAUDE.md`**: replace the placeholder with the same commands.

## Done when

- `cargo build`, `cargo test`, `cargo clippy -- -D warnings` and `cargo fmt --check` pass locally.
- `common` and `client` build for `wasm32-unknown-unknown`.
- `cargo run -p theca-core` starts and exits cleanly.
- `scripts/dev.sh` starts Postgres and writes `.env`; running it again changes nothing.
- The Woodpecker pipeline is green.
