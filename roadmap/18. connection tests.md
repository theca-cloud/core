# Step 18: Connection tests

Goal: an admin checks an SMTP server, a storage or an identity provider while filling in its settings, before saving: "Test connection" for each, and "Send test email" for SMTP (decisions.md, Connection tests: every external service has one). Asked from the homelab deployment: the only way to check SMTP was a password reset and the logs, and a wrong S3 address hung the setup for minutes.

Helpers only: saving SMTP settings never depends on them. A storage keeps its probe at save (decisions.md, First-run setup: a typo fails the setup, not the first upload).

## The endpoints

Each answers `200` with `{ ok, message }` (`api::ConnectionTest`): a failed test is an answer, not a refused request; `message` is the server's answer or the error, as precise as its library gives it.

| Endpoint | Who | What |
|---|---|---|
| `POST /api/v1/admin/smtp/test` | an instance admin, full session | connects, negotiates TLS, logs in, disconnects |
| `POST /api/v1/admin/smtp/send-test` | the same | the same, then sends a short email to the admin's own address, at once (not queued) |
| `POST /api/v1/admin/storages/test` | the same | the storage probe, nothing saved |
| `POST /api/v1/admin/identity-providers/test` | an instance admin, full session | the issuer's discovery: its document, the issuer it declares, its signing keys |
| `POST /api/v1/organizations/{id}/identity-providers/test` | its owner | the same, through the SSRF guard as its logins (unless `oidc_allow_internal_issuers`) |
| `POST /api/v1/setup/storage-test` | the setup token (`X-Theca-Setup-Token`, or none with `SETUP_OPEN`), only while not set up, under `rate_limit_setup_ip` | the storage probe |

- **SMTP takes the dialog's values**: a map of `smtp_*` settings (`null`: the default), merged over the saved ones and parsed by the same `Settings` code as a save, so a bad port is refused the same way (`400 invalid_setting`). Nothing is stored.
- **The storage probe is the existing one** (`storage::probe`): writes a small object, reads it back, compares, deletes. Its body is a `NewStorage`'s backend.
- **The test email**: the instance's name in its subject, a line saying it's a test; to the admin calling it.

## Failing fast

- **SMTP**: a 10 s timeout for the tests (30 s for the queue's sends, unchanged).
- **S3 probes** (the tests, and the probes at setup and when adding a storage): short client timeouts (5 s to connect, 15 s per request) and one retry, instead of `object_store`'s default policy (retries for minutes, built for transient errors): a wrong address fails in seconds with its error. The stores used for files keep the default policy.

## In `web` (its own step, after this release)

- The Email dialog: "Test connection" and "Send test email" beside Save, their outcome inline (success or the error); Save never waits on them.
- The storage dialogs (the admin's "Add a storage", the setup wizard): "Test connection", its outcome inline; Save still probes on the server.
- The identity provider dialogs (the admin's, an organization's): "Test connection" on the issuer, its outcome inline.

## Tests

- SMTP against Mailpit (the CI's): the test passes; the test email arrives at the admin's address; a wrong port or host fails within the timeout with its error; an unparsable `smtp_port` is `invalid_setting`; nothing is saved.
- Storage: a filesystem path and S3 (Garage) pass; a wrong bucket, key or path fails with its error; nothing is saved; the probe of an unreachable S3 address fails within seconds.
- Setup's test: refused without the token (when not open), refused once set up, rate limited.
- Identity providers: the fake provider passes as an instance's; a wrong issuer path and an address nothing answers fail; an organization's owner is refused a local `http` provider by the guard; a member isn't its owner; nothing saved.

## Done when

CI green; released; `web` uses them; the CE pins it.
