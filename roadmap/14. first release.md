# Step 14: First release

Goal: `core` 0.1.0 published: the server image (amd64 and arm64), the `common`, `client` and `core` crates, the browser package, and `openapi.json`, from a merge into `prod`; release candidates from `dev`. The API can't break without the CI saying so.

Design: `../docs/decisions.md` (Repository, CI and releases), `../docs/CONTRIBUTING.md`.

## Versions and changelog

- **Prepared on `dev`, released by merging into `prod`.** `scripts/release.sh` (run on `dev`): the next version from the Conventional Commits since the last release (`git-cliff`: `feat` → minor, `fix` → patch, `!` → major; `0.x` while in beta), written to the workspace's `Cargo.toml`, `CHANGELOG.md` updated, committed as `chore(release): X.Y.Z`. Then `git merge --no-ff dev` into `prod`.
- **The pipeline on `prod` publishes** that version, tags `vX.Y.Z` and creates the Gitea release (changelog, `openapi.json` attached). It refuses a version already released (the release commit is missing).
- No CI pushes to the repository: versions are written by the script, on a developer's machine (`git-cliff` installed).
- **The process is written in `docs/CONTRIBUTING.md`** (every repository releases the same way).

## The server image

- **Cross-compiled, never emulated**: `cargo zigbuild` builds static binaries (`x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`) natively on the CI's architecture; the image only copies them (no Rust compilation under QEMU, which takes hours).
- **`gcr.io/distroless/static`**: no shell, no package manager, CA certificates included (outgoing TLS: S3, SMTP, OIDC), a non-root user. `HEALTHCHECK` with `theca-server healthcheck`. Plain HTTP on 8080: **TLS is the reverse proxy's** (Traefik), whose address goes in `TRUSTED_PROXIES`.
- **Tags**: `prod` → `latest`, `X`, `X.Y`, `X.Y.Z`; `dev` → `rc`, `X-rc`, `X.Y-rc`, `X.Y.Z-rc` (never moving the `prod` ones).
- **Static files**: `WEB_DIR` (env, optional): the server also serves a directory (the web app's build), with `index.html` for unknown non-API paths (an SPA). The CE image (`ce` repo) sets it; the core image alone serves the API only.

## Packages

- **Crates** (`theca-common`, `theca-client`, `theca-core`) on the Gitea Cargo registry (`publish = ["gitea"]`, path dependencies with their version). The CLI and, later, EE pin them.
- **Browser package**: `wasm-pack build crates/client --target web`, published as `@theca/client` on the Gitea npm registry.
- `openapi.json`: attached to the Gitea release (the web app and the SaaS app generate their types from a pinned one).

## API compatibility

- **`oasdiff`** in CI: `openapi.json` against the last release's (from its tag); a breaking change to `/api/v1` fails, unless the release is a major version. Before the first release, nothing to compare.

## Pipeline

- **CI stays short**: feature branches run the four checks only. On `dev`: plus the release-candidate image. On `prod`: plus images, crates, npm package, tag, Gitea release.
- Agents are amd64: arm64 is cross-compiled. The CI image gains `cargo-zigbuild`, `zig`, `wasm-pack`, `oasdiff`.
- Secrets (Woodpecker): `gitea_user`, `gitea_token` (package write, repository write). The buildx plugin is already allowed privileged.

## Not in this step

- The `ce` repository (CE image, compose): it assembles `core` and `web`, so it comes with the web app. CLI binaries: with the `cli` repository.

## Tests

- The image starts, migrates, answers `/api/health`, on both architectures (amd64 natively; arm64 checked as a valid static `aarch64` executable).
- `WEB_DIR`: files served, `index.html` for unknown paths, `/api/...` never shadowed.
- `oasdiff` fails on a deliberately removed field, passes on an added endpoint.
- A dry run of the release script (version computed, changelog written) without committing.
