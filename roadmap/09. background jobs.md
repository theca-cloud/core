# Step 09: Background jobs

Goal: the server cleans up after itself: unreferenced chunks, the trash past its retention, expired tokens, objects without a row. Every run is recorded, survives crashes, and the admin sees and triggers them.

Design: `../docs/decisions.md` (Background jobs, Garbage collection, Storage abuse, Deletion).

## The runner

- **One runner for every job**: a tokio task per job, looping "wait, run". The wait comes from the **last finished run** in `job_run` (`max(0, its start + interval - now)`), so restarts don't starve long-period jobs. **Interrupted runs don't count**: a run cut off by a crash starts again right after the restart (a server dying every 50 minutes still gets its hourly GC through, slice by slice).
- **Each run** is its own spawned task (a panic kills only that run), under a timeout, recorded in `job_run` (start, end, status, items, error). The loop always continues.
- **Startup**: runs left `running` (a crash) are marked `interrupted`. Every job is safe to interrupt anywhere; the next run resumes.
- **Shutdown** (SIGTERM): no new runs; current ones get a few seconds, then are dropped (and marked `interrupted` at the next start).
- **No locks**: one server process per database (decisions.md). A job is a plain `async fn(&AppState) -> Result<items>`, so tests call it directly.
- **Intervals and timeouts are constants** for now (hourly for the GC and the trash, daily for the rest). They become settings with the settings reload (admin API, step 13): a changed setting then applies to the jobs without a restart. Until then, `trash_retention_secs` is read at each run from the settings loaded at startup.

## The jobs

### `chunk_gc` (hourly)

- **Candidates**: chunks no version references, untouched for `gc_grace_period_secs` (the existing setting, 24 h), whose upload URL has expired (`url_expires_at` absent or past); plus tombstoned chunks (a previous run was interrupted).
- **Three steps per chunk** (decisions.md): mark `deleting_at` (lookups and commits now ignore it), delete the object (idempotent), delete the row. A crash between steps leaves a tombstone the next run resumes.
- **A concurrent commit can't lose data**: marking flips the chunk's `ready` (generated), which `chunk_in_version`'s composite FK references, so the database refuses to mark a chunk a commit just referenced, and a commit can't reference a marked one. Marks go in batches; a batch refused by that FK is retried chunk by chunk.
- The quota frees itself: it sums the rows.

### `trash_purge` (hourly)

- Nodes trashed for longer than **`trash_retention_secs`** (new setting, default 30 days; `0` = purged at the next run) are deleted for good, with their subtree and versions (the existing purge, one transaction per trashed node). Their chunks are left to the GC.

### `cleanup` (daily)

- **Tokens**: deletes revoked ones (logouts, used recovery codes, revoked app passwords) and expired sessions (idle or max lifetime).
- **Job history**: deletes `job_run` rows older than 30 days.

### `orphan_check` (daily)

- Lists every backend's objects and deletes **those without a `chunk` row**, logged as an anomaly (`orphan_object`). The safety net for objects stored without being billed (an S3 clock behind ours beyond the `url_expires_at` margin, or any bug).
- An object is only deleted if it's **older than the presigned URL lifetime plus a margin**: rows always exist before their objects (lookup, then upload), so a young object without a row can only be a race in flight.
- Keys that don't parse as a chunk are left alone and logged (a bucket shared with something else is a misconfiguration, not ours to clean).
- Compared in pages (a backend can hold millions of objects).

## Admin API

- `GET /api/v1/admin/jobs`: each job with its last runs (status, items, error, duration).
- `POST /api/v1/admin/jobs/{job}/run`: runs it now (if not already running), returns the run.
- Instance admins only (`account.instance_admin`), from a full session.

## Health

- `/api/health` stays a liveness probe (a failing job must not get the container restarted in a loop), and reports in its body the jobs whose last 3 runs failed.

## Schema changes

- None besides the setting (`trash_retention_secs`); `job_run` exists.

## Not in this step

- Expired invitations (phantom users): with invitations, step 10. Version retention, the consistency check (missing objects): later.
- Huge cross-library moves as a job (the ponytail from step 08): when they show up.

## Tests

- GC: an abandoned chunk is deleted (object and row) after the grace period, not before; a referenced chunk never; a chunk with a valid URL never; an interrupted run (tombstone, object gone or not) is finished by the next; a commit racing the GC either wins (chunk kept) or gets `chunk_missing`, never a version pointing to a deleted object.
- Trash: purged after the retention, not before; `0` purges at once; chunks then go with the next GC.
- Cleanup: revoked and expired tokens go, live ones stay.
- Orphans: an old object without a row is deleted and logged; a young one is kept; a non-chunk key is kept.
- Runner: a run is recorded; a panic and a timeout are recorded as failures and the loop goes on; `running` rows become `interrupted` at startup; the wait comes from the last finished run, interrupted ones ignored.
- Admin API: lists runs, triggers a job; non-admins and restricted sessions refused.
