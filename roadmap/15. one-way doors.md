# Step 15: One-way doors

Goal: every decision that is expensive to change once real data exists is confirmed (and written down) or changed now, while `0.x` may still break anything. After 1.0, later features (`../docs/features.md`, V1's scope) arrive by forward migrations only: new tables and columns, never a rewrite of stored data or objects.

Design: `../docs/features.md` (V1's scope), `../docs/decisions.md`.

## What gets reviewed

Each item ends as one of: **kept** (the reason recorded in `decisions.md`), or **changed** in this step.

- **Storage layout.** Chunk objects are named by the chunk's UUID, flat at the backend's root (`storage.rs`). Questions: a prefix (`chunks/`) leaving room for other object kinds (thumbnails, exports); fan-out directories on the filesystem backend (millions of files in one directory); what the orphan check's listing costs at that scale. Renaming objects later means rewriting every one.
- **Chunk format.** FastCDC parameters (512 KiB / 1 MiB / 8 MiB), `xxh3_128`, LZ4 with the entropy check, and how a stored object records its format (compression, a future encryption). Dedup matches on these: changing one later splits dedup in two.
- **E2EE readiness.** `decisions.md` (E2EE) wraps chunk keys per version-to-chunk reference and uses a keyed dedup hash. Check that the schema takes them as added columns and a library flag, with no rewrite of existing rows; same for the per-node properties and permissions noted for later.
- **IDs and tokens.** UUIDv7 everywhere outside the database; the `th_<public>.<private>` token format; RCS version numbers. Clients store them.
- **The `/api/v1` contract.** From 1.0 on, `oasdiff` fails on breaking changes: a pass over every endpoint for names, shapes and errors we'd regret, fixed now.
- **Migrations after 1.0.** The single migration is frozen at 1.0; later ones are forward-only. A test applies the migrations to a database holding data from the previous release (the fixtures), so an upgrade is tested, not only a fresh install.

## Also in this step

- **Sync with `rclone`**: V1's answer to two-way sync (`features.md`). A section in `CONFIGURATION.md` (WebDAV): `rclone bisync` against the drive, with the flags that work with our WebDAV (checked by hand against `try/`).

## Not in this step

The 1.0 release itself: after the web app and CE (the order: this review, the web app, CE, 1.0, the SaaS).

## Done when

- Every item above is kept with its reason in `decisions.md`, or changed and released (a `0.x` minor).
- The upgrade test exists and runs in CI.
