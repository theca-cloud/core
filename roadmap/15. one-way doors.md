# Step 15: One-way doors

Goal: every decision that is expensive to change once real data exists is confirmed (and written down) or changed now, while `0.x` may still break anything. After 1.0, later features (`../docs/features.md`, V1's scope) arrive by forward migrations only: new tables and columns, never a rewrite of stored data or objects.

Design: `../docs/features.md` (V1's scope), `../docs/decisions.md`.

## What gets reviewed

Each item ends as one of: **kept** (the reason recorded in `decisions.md`), or **changed** in this step.

- **Storage layout.** Chunk objects are named by the chunk's UUID, flat at the backend's root (`storage.rs`). Questions: a prefix (`chunks/`) leaving room for other object kinds (thumbnails, exports); fan-out directories on the filesystem backend (millions of files in one directory); what the orphan check's listing costs at that scale. Renaming objects later means rewriting every one.
- **Chunk format.** FastCDC parameters (512 KiB / 1 MiB / 8 MiB), `xxh3_128`, LZ4 with the entropy check, and how a stored object records its format (compression, a future encryption). Dedup matches on these: changing one later splits dedup in two.
- **E2EE readiness.** `decisions.md` (E2EE) wraps chunk keys per version-to-chunk reference and uses a keyed dedup hash. Check that the schema takes them as added columns and a library flag, with no rewrite of existing rows; same for the per-node properties and permissions noted for later.
- **IDs and tokens.** UUIDv7 everywhere outside the database; the `th_<public>.<private>` token format; RCS version numbers. Clients store them.
- **The `/api/v1` contract.** From 1.0 on, `oasdiff` fails on breaking changes: a pass over every endpoint for names, shapes and errors we'd regret, fixed now.
- **Migrations after 1.0.** The single migration is frozen at 1.0; later ones are forward-only. A test applies the migrations to a database holding data from the previous release (the fixtures), so an upgrade is tested, not only a fresh install.

## Findings

Reviewed with the user before any change.

**Changed:**

- **Storage layout**: objects at `chunks/<aa>/<bb>/<uuid>`, `aa` and `bb` the UUID's last four hex digits (UUIDv7 starts with a timestamp: its tail is the random part, so recent chunks spread evenly). Two levels: 65,536 directories, ~150 chunks each at 10 million. The `chunks/` prefix leaves room for other objects (thumbnails, exports) and bounds the orphan check's listing. The same layout on S3 (request rates scale per prefix).
- **Dates in the API**: they were Postgres's `::text` (`2026-10-07 18:42:41.390502+00`: not RFC 3339, unreliable for JavaScript's `Date`, its offset following the database server's `TimeZone`). Now `DateTime<Utc>` (`chrono`, already a dependency) in the `common` types: RFC 3339 in UTC, `format: date-time` in `openapi.json`, read from `timestamptz` by sqlx without casts.

**Kept** (reasons in `decisions.md`):

- Chunk format: `xxh3_128` (already reasoned: dedup only within declared trust); FastCDC parameters can change without breaking anything (dedup efficiency only); the compression is recorded per chunk, unknown algorithms decode as `Unknown`; encryption will be one more such column.
- E2EE: added later as columns (`wrapped_key` on `chunk_in_version`, `node`, `library_member`; a library flag; the account's key pair; the keyed BLAKE3 hash in the same 16-byte column). Only `stored_size ≤ plain_size` loosens: a constraint change, no data rewritten.
- IDs and tokens: UUIDv7 (its creation time is public anyway), `th_<public>.<private>`, RCS version numbers.
- Encrypted secrets (`base64(nonce ‖ ciphertext)`): no version prefix, but one can be added later (`v2:`; base64 has no `:`), so a key rotation needs no format break.
- Lists as arrays (decided: lists everywhere, big listings streamed); pagination, if ever, comes as optional query parameters.

**Gaps for the web app** (not one-way doors; a core step planned with the web app): library members (V1, roles `read`/`write`) have no endpoints, only the creator becomes one; dedup namespaces can be given to `POST /libraries` but not created or listed; users can't create a company organization (only an admin), owners can't rename theirs.

**Moved, still V1:**

- **The upgrade test** goes with the 1.0 step: until then the single migration is rewritten in place, so there is no older database to upgrade. At 1.0 the migration freezes and the test starts (a database holding the previous release's data, migrated forward).
- **Sync with `rclone`** (V1's answer to two-way sync, `features.md`) goes with the CE step: user documentation, `rclone bisync` against the drive with the flags that work with our WebDAV, checked by hand against a CE instance.

## Not in this step

The 1.0 release itself: after the web app and CE (the order: this review, the web app, CE, 1.0, the SaaS).

## Done when

- Every item above is kept with its reason in `decisions.md`, or changed and released (a `0.x` minor: 0.8.0, `../docs/BREAKING.md`).
