# Step 06: Identity and authentication

Goal: real users log in (password + TOTP, or OIDC), and every API request is authenticated. The temporary `X-Theca-User` header disappears.

Design: `../docs/decisions.md` (Authentication, Multi-tenancy, Authorization), `../docs/db.md`.

## What's already there

- Schema: `account`, `identity` (kinds `password`, `oidc`, details checked per kind), `user`, `token` (usages, prefix + SHA-256), `library_member`.
- The `CurrentUser` extractor, which becomes `CurrentAccount` (see below).
- The server key (`JWT_KEY__FILE`, renamed `SERVER_KEY__FILE`: there's no JWT), loaded or generated at startup.

## Sessions and tokens

No JWT (see decisions.md, Authentication): every credential is an opaque token (`th_<public>.<private>`, prefix + SHA-256 in `token`), looked up on every request in one query that also slides `last_seen` (written at most every 5 minutes).

- **Login** (`POST /api/v1/auth/login`): email + password (+ TOTP code if enabled) → a session token (usage `session`, resource = the account, named after the user agent) in the `theca_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`). Sliding: valid while used at least once every `session_idle_lifetime_secs` (default 7 days), optionally capped by `session_max_lifetime_secs` after login.
- **No "current organization"**: every resource belongs to one organization (a library through `owner`; nodes, versions, chunks through their library), so the server acts as **the account's membership in the resource's organization** (joined memberships only). Hence:
    - one browser can work on several organizations at once;
    - endpoints without a resource name the organization (`POST /libraries` takes `organization`); listings return every organization's items, each with its organization;
    - `declared_by` and the per-account upload cap use the user resolved from each chunk's organization.
- **Access checks in one place**: SQL functions `organization_access(token)` and `library_access(token)` combine the joined memberships, the library roles, and the token's scope (organization, library) and read-only cap. Every query that touches a library joins them.
- **Logout** (`POST /api/v1/auth/logout`): revokes the session (reason `logout`), immediately.
- **Sessions list / revoke** (`GET /api/v1/auth/sessions`, `DELETE .../{id}`): name, user agent, IP, last seen.
- **App passwords** (usage `app_password`, resource = the account): create (shown once), list, revoke. Sent as is: `Bearer` (CLI, API clients), Basic auth (WebDAV, step 11).
    - Scope: the account, an organization, or a library; optionally read-only (a cap on top of the membership's role).
    - Created from a session only, within what it reaches: a restricted session creates, lists and revokes only app passwords inside its organization.
    - Data only: no login, no app passwords, nothing on the account, identities or sessions.
- **Every token has a name** (`NOT NULL`).
- **CSRF**: `SameSite=Lax`, and cookie-authenticated `POST`s must carry `Content-Type: application/json` (or `X-Theca-CSRF`), checked by a middleware. Only `POST`: a cross-site form can only send `GET`/`POST`, any other method needs a CORS preflight.

## Passwords and TOTP

- **Argon2id** (`argon2`), hash in `identity.details.hash` (PHC string, parameters included, so they can evolve).
- **TOTP** (`totp-rs`), the second factor of password logins (not of OIDC, nor app passwords): an `identity` of kind `totp`.
    - Setup from a full session: `POST /auth/totp` (secret + `otpauth://` URI, stored unconfirmed), `POST /auth/totp/confirm` with a first code (returns 10 recovery codes), `POST /auth/totp/disable` and `POST /auth/totp/recovery-codes` with a current code or a recovery code.
    - Login in one request: right password, no code → `totp_required`; the client sends email, password and code again.
    - Codes: ±1 step, each step used once (`details.last_step`). Recovery codes: 80 bits, hashed with the account, single-use, in `token` (usage `recovery_code`).
    - The secret is **encrypted** (XChaCha20-Poly1305, the account as associated data) with a key derived from a new secret, **`DATA_KEY__FILE`**: mandatory variable, the file may be empty and is then filled by the server. A database dump alone can't produce codes.
- Accounts are created by the setup wizard (step 07), registration and invitations (step 10); here, by tests and a `db` function.

## OIDC

- **`identity_provider`** table: `organization` (**NULL = instance-wide**, configured by the instance admin; set = configured by that organization), name (unique per organization), issuer, `client_id`, **`client_secret_file`** (the path, never the secret), enabled.
- **`identity.provider`** → `identity_provider`, set if and only if `kind = 'oidc'`; uniqueness on `(provider, subject)`.
- Authorization code flow with PKCE (`openidconnect`, over our `reqwest`): `GET /api/v1/auth/oidc/{provider}/start` → provider → `GET .../callback` → session, redirecting to `/` or `/login?error=<code>`. The flow's state in an encrypted cookie. `GET /auth/oidc/providers` lists the instance-wide providers.
- **The provider decides the session's scope.** A provider can assert anything (any subject, any "verified" email), so trust comes from who controls it:
    - instance-wide provider, or password: **full session** (the whole account);
    - an organization's provider: **restricted session**, carrying that organization (the session's `token` row). Every access check refuses resources of other organizations.
    - Without this, an organization's admin could run their own IdP, assert a victim's email, and reach the victim's personal organization and other companies.
- **Account-level actions require a full session**: password, identities, TOTP, sessions of other devices, accepting invitations, deleting the account. Otherwise an organization's SSO could add its own password and escape the restriction.
- **Linking**: manually, from a full session (`POST /auth/oidc/{provider}/link`, CSRF-protected, returns the provider URL; any provider, the scope still comes from the provider); and **by matching the email** when the instance setting allows it (`oidc_link_by_email`), only if the provider marks the email verified.
- An unknown subject with no matching account: refused (a new account once registration exists, step 10).
- Identities: `GET /auth/identities`, `DELETE /auth/identities/{id}` (never the last way to log in).
- When a member leaves an organization, their identities through that organization's providers are deleted (trigger).
- Deferred: managing providers through the API (tests and admins insert rows), discovery caching, SSRF checks on organization-configured issuers.

## Errors and anomalies

- Wrong credentials: one generic error (`invalid_credentials`), whether the email exists or not, and the same time spent (hash computed even for unknown emails), so accounts can't be enumerated.
- Anomalies: failed logins (account if known, IP), a revoked or unknown token (possible theft), TOTP failures. Rate limiting stays in step 13.

## Tests

- Login → cookies → authenticated request; wrong password, unknown email (same error, same timing order of magnitude), TOTP required and checked.
- Revoked session → refused at once; 7 days of inactivity → expired; `last_seen` throttled.
- An account in two organizations works on both in the same session; each request acts as the membership of the resource's organization; nothing from an organization the account isn't a member of (or only invited to) is reachable.
- App passwords: each scope (account, organization, library, read-only) reaches exactly what it should; can't log in or act on the account; revoked → refused; a restricted session can't create one outside its organization.
- CSRF: a cookie-authenticated `POST` without JSON content type refused.
- OIDC against a fake provider (an in-process OIDC server in the tests): login, unknown subject, linking by email (on/off, verified only), manual linking.
- **The takeover scenario**: an organization's provider asserting another account's email gets a session restricted to that organization, which can't reach the account's other organizations nor do account-level actions.
- TOTP secrets are stored encrypted (a DB read alone doesn't reveal them).
- Every step-04/05 test keeps passing with real authentication instead of `X-Theca-User`.

## Schema changes

- `identity_provider` table; `identity.provider` with its CHECK and the `(provider, subject)` uniqueness (replacing `(issuer, subject)`); identity kind `totp`.
- `token`: `name` (NOT NULL), `organization` (restricted sessions, app password scope), `library`, `read_only`.
- Functions `organization_access`, `library_access`.
- Settings: `oidc_link_by_email` (default off), documented in `CONFIGURATION.md` with `DATA_KEY__FILE`.
